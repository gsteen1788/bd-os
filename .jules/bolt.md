## 2024-03-20 - O(1) group lookup over O(N*M) loop filtering
**Learning:** Calling `.filter()` on an entire collection (like `opportunities` or `protemoi`) inside a render loop over a finite set of categories (like `stages`) introduces an $O(S \times E)$ performance bottleneck. This pattern causes unnecessary repeated array iterations when $E$ (entities count) grows, delaying main-thread rendering.
**Action:** When a screen needs to display items grouped by a category property (e.g. kanban columns or board stages), proactively use `useMemo` to group the entities into a `Map` in a single $O(E)$ pass. Inside the render map over the categories, use `$map.get(category) || []` for an $O(1)$ constant-time lookup.
## 2024-03-22 - Anti-pattern: Memoizing infrequent onClick array searches into the render loop
**Learning:** Extracting an \(O(N)\) array search (`array.find()`) that originally executed only during an infrequent `onClick` callback into a `useMemo`-generated `Set` causes the computation and memory allocation to happen on *every render* when dependencies change. This degrades performance instead of improving it.
**Action:** When identifying loop optimizations, distinguish between computations that happen synchronously during the render cycle (e.g. filtering a list to display) versus computations that happen asynchronously in event handlers (e.g. `onClick`). Only memoize render-blocking operations. Let event handlers perform their localized \(O(N)\) lookups.
## 2024-03-23 - Anti-pattern: Unmemoized intermediate array filters breaking downstream useMemo caches
**Learning:** If you filter an array during a React render cycle (e.g., `const filtered = items.filter(...)`) and then pass that `filtered` array as a dependency to a downstream `useMemo` hook, the `useMemo` cache will be busted on *every single render*. This happens because `filter` returns a new array reference each time, silently destroying intended performance optimizations (like O(N) grouping operations).
**Action:** Always wrap intermediate array transformations (like `.filter` or `.map`) in their own `useMemo` block if their output is used as a dependency in downstream hooks. This preserves reference equality and ensures subsequent optimizations work as intended.
## 2024-03-30 - O(1) global index lookup over O(N^2) loop indexOf
**Learning:** Calling `array.indexOf(item)` inside a `.map()` or rendering loop effectively creates an \(O(N^2)\) algorithmic complexity bottleneck. This happens because for every element being mapped, an \(O(N)\) linear search is triggered to find its position.
**Action:** When an index is needed during rendering (e.g. for sequential numbering or anonymized labeling) over a dynamically filtered array, use `useMemo` to pre-calculate a global index `Map` once per dependency update. Use `$indexMap.get(item.id)` for an \(O(1)\) lookup during the render loop.
## 2024-04-05 - Avoid repeated date parsing in render loop maps
**Learning:** Pre-parsing date strings to `Date` objects inside individual string formatting utility functions (e.g. `formatDate(str)`, `formatTime(str)`) within a mapped component array creates redundant iterations of object instantiations inside the render loop. If a single item's date needs multiple formats, it parses the same string repeatedly.
**Action:** When a `.map` loop needs to display multiple formatted versions of the same date property (like date AND time), instantiate the `Date` object once at the start of the item's map callback and pass the parsed `Date` object directly into formatting functions to avoid redundant parsing and reduce garbage collection overhead.
## 2024-03-12 - Prevent $O(N)$ Date parsing in controlled components
**Learning:** Instantiating `new Date(task.dueDate)` and `new Date()` within a `.map` function inside a React render loop causes massive memory allocation and garbage collection overhead, especially when inside a component with a controlled input (like `AdminTaskBar`). Typing in the input re-renders the component on every keystroke, forcing thousands of redundant `Date` object instantiations and date formatting calls.
**Action:** When mapping over lists that require date parsing or formatting, hoist the calculation into a `useMemo` block that depends on the list. Derive lookups (`Map`) for parsed dates, overdue status, or formatted strings, and use these $O(1)$ lookups in the render loop instead of recalculating on every frame.
## 2024-05-14 - Anti-pattern: Pre-mature Optimization with High Entropy Values
**Learning:** Optimizing repeated operations by wrapping them in a generic cache (e.g. `Map` inside `groupItemsByWeek`) backfires when the input values have high entropy (e.g. unique timestamps). In these cases, the cache never hits, leading to memory bloat and performance degradation from `Map` insertions and lookups.
**Action:** Before introducing a caching mechanism for an operation, assess the variance of the inputs. If the inputs are unique strings or objects, favor optimizing the caller context (like hoisting the operation outside a loop into `useMemo` in a React component) rather than adding a generic, low-hit-rate cache inside the utility function.
## $(date +%Y-%m-%d) - Pre-parse Date inside loops
**Learning:** Found that `Intl.DateTimeFormat.format()` combined with `new Date()` inside `.map()` loops causes expensive memory allocations and garbage collections.
**Action:** Always pre-calculate and memoize `Date` objects inside a `useMemo` block with a `Map` structure to prevent $O(N)$ reinstantiation inside React render loops.
